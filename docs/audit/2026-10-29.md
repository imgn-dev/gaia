# Code audit, 2026-10-29

Audit of gaia at `1a598c9` (0.1.2-SNAPSHOT): correctness, security, good practice and test coverage of every
module, the build, the CI workflows and the release scripts.

## Method

Six read-only reviews ran in parallel, one per area. Each finding was checked against the code; most of the
behavioural ones were also reproduced, against the built classes, with jshell or javac. The key findings of each area
were re-read in the sources before writing this report. Nothing was changed in the repository.

Severity:

- **High**: wrong results, a crash, a deadlock or a failed build in normal use.
- **Medium**: a real defect that needs particular input or timing, or a security weakness with a plausible path.
- **Low**: an edge case, a misleading message or document, or a hardening opportunity.
- **Info**: a remark or a decision to make, not a defect.

"Plausible" findings were reasoned through but not reproduced; each needs a test before it is fixed.

## Summary

The code is in good shape for its age: contracts of the JDK interfaces are respected almost everywhere, inputs are
checked, the build is strict (Error Prone, NullAway, Checkstyle, `-Werror`) and the release flow keeps secrets out of
command lines. No finding lets an outside party attack a user of the libraries.

The findings that matter most:

| # | Severity | Area | Finding |
|---|---|---|---|
| 1 | High | memfs | Lock-order inversion between `FileLock.release()` and `tryLock()`: two threads deadlock |
| 2 | High | processor | A listener whose methods resolve in different rounds gets a partial index, then an error |
| 3 | High | processor | The generated index breaks `-Xlint:all -Werror` in an exported package of a named module |
| 4 | Medium | core io | `AtomicFiles` writes into a temporary file that is briefly readable by everyone |
| 5 | Medium | core io | `DecodingOutputStream` writes the decoded text twice after a coding error |
| 6 | Medium | core event | One broken `SubscriberIndex` provider makes every `register()` fail |
| 7 | Medium | core collect | Serial forms allocate arrays sized from the stream: a 151-byte stream exhausts the heap |
| 8 | Medium | processing | `$T.member` is rewritten to a bare name that can mean something else, or nothing |
| 9 | Medium | processing | `Method.overriding` copies `native`: overriding `hashCode()` crashes the processor |
| 10 | Medium | CI | Build code runs with a write token and the signing key in reach |

## core: `base`, `collect`, `text`, `time`

No high-severity issue. Equality across implementations, unmodifiability, ordering and fail-fast iteration all hold.

### Medium

**Serial forms trust the length they read.**
`collect/SerializedMultiset.java:72-73`, `SerializedMultimap.java:69-70,80`, `ImmutableOrderedSet.java:203`,
`ImmutableOrderedMap.java:332-333`. `readObject` reads an `int` and allocates `new Object[length]` (and `int[]`,
`Object[][]`) before reading a single element. An `ObjectInputFilter` with `maxarray` does not help, because these arrays
are allocated by hand, not deserialized. A serialized one-element `HashMultiset` with its length patched to
`0x7ffffff0` (151 bytes) throws `OutOfMemoryError` under `-Xmx512m`. Fix: grow from `min(length, 1024)`, or read
each element straight into the builder.

**`MoreGatherers.max` and `min` are quadratic on ascending input.** `java24/.../collect/MoreGatherers.java:507-526`.
Each kept element is inserted with `ArrayList.add(low, e)`; on ascending input that is always index 0. Measured:
129 ms for 50,000 elements, 1.9 s for 200,000; descending input takes 9 ms. The Javadoc's "one comparison" is only
true of rejected elements. Fix: a bounded heap keyed by element and encounter index, sorted in the finisher.

### Low

- **`NamingConvention` produces names its own conventions reject.** `text/NamingConvention.java:201,210-215`.
  Validation uses `isLowerCase`/`isUpperCase` but conversion uses `toUpperCase(int)`, which leaves `ß` unchanged:
  `LOWER_UNDERSCORE.toUpperUnderscore("straße")` gives `STRAßE`, which `UPPER_UNDERSCORE` then rejects.
  `NamingConventionTest:119-120` pins the inconsistent output (`GRÖßE_ÄNDERUNG`). Fix: validate against the conversion
  (`toUpperCase(cp) == cp` for upper conventions, and the mirror for lower ones).
- **Bulk removals from a list multimap's values are quadratic.** `collect/AbstractMapListMultimap.java:37-132`.
  `removeIf`, `removeAll`, `retainAll` and `subList(a, b).clear()` remove one element at a time. Fix: override
  `removeIf` and `removeRange` to delegate to the backing list, then adjust the size.
- **Multisets beyond `Integer.MAX_VALUE` occurrences.** `AbstractMapMultiset.java:40`. `size()` is capped as
  documented, but the default spliterator reports the capped size as exact: `stream().count()` gives 2147483647 for
  `MAX_VALUE + 5` occurrences. `toString()` and `toArray()` try to materialise every occurrence. Fix: a spliterator that
  is not `SIZED` past the cap; `element × n` in `toString`.
- **`Multisets.multisetCopy` trusts a foreign `Multiset`.** `collect/Multisets.java:62-63`. `forEachEntry` is not
  checked for null elements or non-positive counts, so a broken user implementation yields an "immutable" multiset
  holding null, or an element with count 0 that `contains` reports.
- **`Maps` says "exactly like `Map.of`", with one deliberate exception.** `map(...).entrySet().contains(null)` throws,
  where `Map.of` returns false (`ImmutableOrderedMap.java:248`, pinned by `MapsTest:206`). Document the exception.
- **Avoidable work on hot paths.** `AbstractMapMultiset.add`, `remove` and `setCount` call the varargs `checkArgument`
  on every call, boxing ints and allocating an array; `Version.parse` builds an error-message fragment on every
  successful parse (`Version.java:96`).

### Info

- `Stopwatch.toString` picks its unit before rounding: 999,960 ns prints `1000 μs`, 59.999 s prints `60.00 s`, and
  10,000 days prints `1.000e+04 d` (`time/Stopwatch.java:171-172`).
- Serial proxies fail inconsistently on a tampered stream: the multiset proxies throw `InvalidObjectException`, the
  ordered set and map proxies throw `NullPointerException` or `IllegalArgumentException` from `readResolve`.
- `Range.open(3, 3)` fails with "the lower bound is above the upper bound"; the real reason is an open range with equal
  bounds (`Range.java:48-51`).

### Plausible

- `AbstractMapMultiset.OccurrenceIterator` (263-307) snapshots the count of each entry: after `setCount(e, 1)` during
  iteration it keeps returning `e`, and a later `remove()` fails with `IllegalStateException`.
- A list multimap's value view is not fail-fast against changes made through the multimap itself
  (`mm.put(k, v)` during `for (v : mm.get(k))`): elements can be skipped silently.

## core: `io`, `platform`, `system`, `event`

### Medium

**`AtomicFiles` writes through a temporary file created with default permissions.** `io/AtomicFiles.java:87-90,139-154`.
`Files.createFile` creates the file as `0666 & ~umask`, usually `0644`; `copyPermissions` narrows it afterwards. Between
the two, another local user can open the temporary file of a `0600` target in a world-readable directory, and keep
reading it once the secret is written: permissions are checked at `open()` only. Fix: create the file with the
target's permissions as a creation attribute (owner-only for a new file), ideally as one `FileChannel.open(tmp,
CREATE_NEW, WRITE, attr)` used for the whole write, which also closes the window where the path is reopened by name.

**`DecodingOutputStream` duplicates output after a coding error.** `io/internal/DecodingOutputStream.java:85-95`.
`decode` throws before `bytes.compact()`, leaving the buffer flipped; the `close()` that try-with-resources runs flips
it again and decodes the prefix once more. Writing `{'a','b','c',0xFF}` through `CharSink.asByteSink(UTF_8)` throws
`MalformedInputException` and leaves `abcabc` in the sink. Fix: compact in a `finally`, or remember the failure and skip
decoding in `close()`.

**One broken provider breaks the event bus.** `event/EventBus.java:317-333`. `loader.stream().map(Provider::get)`
instantiates providers until one matches; a provider that cannot be loaded or instantiated throws
`ServiceConfigurationError` out of the stream. A stale `META-INF/services` entry, common after an incremental build in
an IDE, then makes every `register()` that reaches it fail, including lookups for classes that have no index, and
`ClassValue` caches nothing, so it fails again on every call. Fix: iterate the providers one by one and skip, and log,
those whose class or constructor fails, still matching on `listenerType()` rather than on the generated name.
Untested.

### Low

- **Slices can read outside their range.** `io/internal/SlicedByteSource.java:95-99`: `skip(-8)` on a slice of a
  `FileInputStream` seeks backwards and increases `remaining`; the stream then returns 11 bytes from a 3-byte slice.
  Fix: `if (count <= 0) return 0;`.
- **`EncodingInputStream` returns zeros after a coding error.** `io/internal/EncodingInputStream.java:70-76`: after the
  exception, the buffer is left in write mode and the next reads return `0 0 0`. Fix: flip in a `finally`, or rethrow
  the stored failure.
- **`CharSink.writeLines(Iterable)` reads the iterable twice** (`io/CharSink.java:121-124`): a one-shot iterable is
  consumed by the null check, and the file is truncated to nothing. Document it, or copy to a list first.
- **Arrays miss their array supertypes.** `event/EventBus.java:285-299`: `publish(new String[] {"x"})` does not reach
  a subscriber of `Object[]`, although the class promises delivery to all supertypes. Reject array event types in
  `subscribe`, as `@Subscribe` already does, or add the array supertypes.
- **Temporary names can exceed `NAME_MAX`.** `io/AtomicFiles.java:142` adds about 19 characters; a 240-byte file name
  fails where `Files.write` succeeds. Truncate the embedded name.
- **Relative Windows variables are accepted.** `platform/internal/WindowsDirectories.java:45-51`: `APPDATA=.` makes
  every directory relative to the working directory. XDG variables are already checked for being absolute; do the
  same here.
- **`ApplicationDirectories.checkName` accepts names Windows mishandles** (`platform/ApplicationDirectories.java:79-97`):
  `CON`, `NUL`, `COM1`…`LPT9` (with or without an extension) and names ending in a dot, which Win32 strips, so `Quuz.`
  and `Quuz` are the same directory. The Javadoc says "valid on every platform".
- **`ByteSource.of(URL)` has no timeouts** (`io/ByteSource.java:84-87`): a stalled HTTP server blocks forever, and
  `read()` buffers any body size. Document it as meant for local resources, or set timeouts.
- **A rejection by the bus executor is undocumented** (`event/EventBus.java:200-202`): `RejectedExecutionException`
  propagates out of `publish()`, while the Javadoc only covers subscribing-annotation executors.

### Info

- Each bus creates an executor per subscribing annotation and never shuts it down: many short-lived buses with a
  thread-owning executor class leak threads, or the class loader of a plugin. Document the expected life cycle.
- `AtomicFiles` replaces a dangling symbolic link with a regular file (`Files.exists` is false for it); the Javadoc only
  covers links to existing files.
- `SystemProperties.javaHome`, `userHome`, `userDir`, `javaIoTmpdir` and `javaClassPath` changed from `String` to `Path`
  or `List<Path>` since 0.1.1: a binary-incompatible change the release notes should mention.

### Plausible

- In a directory that others can write to and that has no sticky bit, `AtomicFiles` reopens the temporary file by name
  (`FileChannel.open`, `setPosixFilePermissions`), both following symbolic links: swapping the file in between could
  redirect the write. The single-channel fix above removes this.

## memfs

### High

**Deadlock between releasing a lock and taking another.** `internal/MemoryFileLock.java:23-34`,
`internal/RegularFile.java:149-165`. `MemoryFileLock.release()` holds the lock's monitor and then takes `fileLocks`;
`RegularFile.lock()` holds `fileLocks` and calls `held.isValid()`, which is `synchronized` on the held lock. Thread A
closing a channel while thread B calls `tryLock` on another region of the same file hang forever. Fix: make `valid` an
`AtomicBoolean` or `volatile`, drop `synchronized` from `isValid` and `release`, and never call into a lock while holding
`fileLocks`.

### Medium

- **An open file can lose its content to a concurrent delete.** `internal/FileOperations.java:111-121`,
  `MemoryFileChannel.java:50`, `RegularFile.java:136-146`. The channel registers itself as opened after the tree lock is
  released; a `delete` in that gap sees no open channel and truncates the file, against the documented "kept until the
  channel closes". The same gap lets a channel stay open on a file system that has just been closed. Fix: call
  `file.opened()` inside the `writing()` block.
- **`WatchService.close()` wakes one blocked `take()` only.** `internal/PollingWatchService.java:125-135,157`. A second
  waiting thread blocks forever; the specification wants every one to get `ClosedWatchServiceException`. Fix: requeue
  the wake-up key before throwing.
- **Watch keys of deleted directories stay valid forever**, and the service keeps the directory
  (`internal/PollingWatchService.java:100-110,214-217`): a `while (key.reset())` loop never ends. Cancel and signal the
  key when its directory is unlinked.
- **Watch events grow without bound** (`internal/PollingWatchService.java:202-211`): events are never merged and
  `count()` is always 1. Merge repeats of the same kind and name, and cap the list with `OVERFLOW`.
- **Equal Windows paths can have different hash codes** (`internal/MemoryPath.java:232-249`): `equals` folds case
  character by character, `hashCode` lower-cases the whole string. `C:\ſ` equals `C:\s` but hashes differently, which
  breaks `HashMap` and `HashSet`. Hash each character as `toLowerCase(toUpperCase(c))`.
- **Copying or moving onto an empty root links the file inside it** (`internal/FileOperations.java:317-334,351-360`):
  `Files.copy(src, D:\, REPLACE_EXISTING)` with an empty `D:\` makes `Files.list` show `D:\D:\`. Refuse to replace a
  root.
- **Some attributes can be changed without permission.** `internal/AttributeViews.java:125-130,231-233,306-317`,
  `MemoryFileSystemProvider.java:330-333`: `dos` flags, basic times and `user:` attributes have no access check, so a
  non-owner can clear `dos:readonly` on another user's file and then write it. Require write access, or ownership for
  explicit times.

### Low

- `toAbsolutePath()` of `D:dir` with a working directory on `C:` returns `D:dir`, still relative; its `toUri()` cannot
  be turned back into a path (`internal/MemoryPath.java:211-214`). `FileTree.absolute` already gets this right; share it.
- The entries of a child secure directory stream are resolved against the wrong base: `sub/x` instead of
  `/data/sub/x` (`internal/MemorySecureDirectoryStream.java:30-34`, `FileOperations.java:476-478`).
- A write at a position near `Long.MAX_VALUE` overflows and throws `IndexOutOfBoundsException` instead of an
  `IOException` (`internal/RegularFile.java:75-87`); a zero-length write past the end grows the file, which the JDK does
  not.
- `Files.copy` fails on files of 2 GiB or more (`Math.toIntExact`, `internal/FileOperations.java:306`), which the default
  4 GiB capacity allows, and buffers the whole file on the heap. Copy block by block.

### Plausible

- `transferTo` can loop forever on a non-blocking target that keeps accepting 0 bytes
  (`internal/MemoryFileChannel.java:216-218`).
- `IGNORE_CASE_UNICODE` treats `straße` and `strasse` as the same name, which neither APFS nor NTFS does, while the
  Javadoc says "as on macOS and Windows" (`NameMatching.java:17`, `internal/Names.java:24`).
- A file can be created in a deleted working directory and is then unreachable but still counted
  (`internal/FileOperations.java:165-172`).
- With a fixed `InstantSource`, which tests often use, the watch service never reports `ENTRY_MODIFY`: it compares
  modification times only (`internal/PollingWatchService.java:189`).
- `CREATE_NEW` through a dangling symbolic link creates its target, where the JDK fails.
- Closing a file system makes its files unreachable but does not free them while a `Path` is reachable; the comment at
  `internal/FileOperations.java:289` about `DELETE_ON_CLOSE` and replaced files is wrong.

### Info

- `Configuration.Builder` has no `@since`.
- There are no multi-threaded tests apart from one wake-up test, although the module promises thread safety.

## processing

### Medium

**`$T.member` can become a bare name that means something else.** `source/CodeWriter.java:315-332`. The rewrite only
checks that the member is statically imported:

- with `Objects.*` imported, `$T.toString(x)` and `$T.equals(a, b)` become `toString(x)` and `equals(a, b)`, which
  resolve to the inherited `Object` methods and do not compile; so does any method the generated class declares under
  that name;
- with both `Integer.*` and `Long.*` imported, `$T.MAX_VALUE` becomes an ambiguous `MAX_VALUE`;
- with `Map.*` imported, `$T.Entry` becomes `Entry`, which a single-type import of another `Entry` shadows.

Fix: rewrite only when exactly one static import supplies the name and neither `Object` nor a type of the file declares
it.

**Anonymous classes in code blocks are ignored when choosing imports.** `source/CodeWriter.java:140-150`.
`declaredNames` walks nested types and enum constant bodies but not the anonymous `Type`s passed as `$L`. An anonymous
`Thread` subclass whose body refers to an imported `com.app.State` actually gets `Thread.State`. The `Type` Javadoc
(lines 43-47) promises that supertypes bring their member names along. Fix: also walk the `Type` arguments of code
blocks.

**`Method.overriding` copies `native`, `synchronized` and `strictfp`.** `source/Method.java:172-178`, verified.
`Method.overriding(hashCode).addStatement(...)` throws `IllegalStateException("A method that is NATIVE has no code")`,
which escapes the step and crashes javac; `strictfp` triggers a lint warning since Java 17, fatal under `-Werror`.
Fix: also remove `NATIVE`, `SYNCHRONIZED` and `STRICTFP`; test with `Object.hashCode`.

### Low

- **`GeneratedSources` treats every `FilerException` as "already written"** (`GeneratedSources.java:210`, verified).
  javac also throws it for a hand-written type of that name, an illegal name, or a module it cannot determine; `write`
  then silently returns `false`. Return `false` only for names created in this compilation, and report the others.
- **The text path does not qualify `java.lang` types hidden by the package** (`SourceScope.java:191-201`):
  `scope.name(Character.class)` writes `Character` in a package that declares its own `Character`.
- **Inherited annotation mirrors crash `Diagnostics` and `ProcessingException`** (`Diagnostics.java:139`): a mirror from
  `inheritedAnnotation(...)` is not among the element's own mirrors, and the constructor throws
  `IllegalArgumentException` instead of reporting. Documented, but easy to fall into; fall back to the element.
- **`*/` in Javadoc text closes the comment** (`source/CodeWriter.java:641`). Escape it as `*&#47;`.
- **Restricted identifiers are accepted as type names**: `var`, `yield`, `record`, `sealed` and `permits` pass
  `isIdentifier && !isKeyword` in `ClassName` (line 56), `Type` (243) and `TypeVariableName` (38), and `class record {}`
  does not compile.
- **Deferred elements are reported on top of real errors** (`StepProcessor.java:186`): after an error, javac goes
  straight to the last round, so elements only waiting for another processor get an extra "still deferred" error.
  Skip that report when errors were raised.
- `AnnotatedElements.rootElements()` (line 80) and `Step.processesRootElements()` (line 137) lack `@since 0.1.2`.

### Plausible

- With `--module-source-path`, the filer probably cannot map `CLASS_OUTPUT` resources to a module, and `ServiceFiles`
  would report a misleading "already created" error (`ServiceFiles.java:206,347,364`).
- `ClassName.generatedName(ExecutableElement, …)` counts implicit methods (an enum's `valueOf(String)`, a record's
  accessor) as overloads, and `getEnclosedElements()` does not specify their order, so numbers may differ between
  compilers or between source and class files. `indexOf(method) + 1` silently gives 0 if the method is not found by
  `equals`; throw instead.
- Methods whose names differ only in case get generated names that differ only in case, which collide on the default
  macOS and Windows file systems. Deep packages in `generatedNameIn` can exceed 255 bytes.
- `internal/ElementKey.java:76-81` keys methods by the simple names of their parameter types, so `m(java.util.Date)`
  and `m(java.sql.Date)` collide, and a deferred element could come back as the other overload.
- `TypeName.of` on an annotated error type parses `type.toString()` (line 76), which may start with `@`.

The uniqueness of `ClassName.generatedName*` was re-derived by hand and holds; the exhaustive test covers it.

## processor

### High

**A listener whose methods resolve in different rounds breaks the build.** `SubscribeStep.java:80-94,110-113`,
verified. `StepProcessor` defers each method whose signature has an unresolved type, and the step builds the index from
the methods of the current round only. With `onText(String)` and `onGen(Gen)`, where another processor generates `Gen`:
round 1 writes `$Listener$$Subscribers` with `onText` only, round 2 fails with "Cannot generate …: a type has that name
already". Fix: when any annotated method of a class is deferred, defer the whole class.

**The generated index breaks `-Xlint:all -Werror` in an exported package.** `SubscribeStep.java:140-150`. In
`module m { requires be.imgn.gaia.core; exports p; }`, the generated class alone triggers `[missing-explicit-ctor]`
and twice `[exports]` (`SubscriberIndex` is not reached through `requires transitive`). The parent POM compiles with
`-Werror`, so every be.imgn project hits it. The existing module test passes only because its package is not exported.
Fix: generate an explicit public constructor, and `@SuppressWarnings("exports")` on the generated type.

### Medium

- **Deprecated members warn in generated code** (`SubscribeStep.java:119-137,147`): a `@Deprecated` subscriber method,
  event type or executor gives `[deprecation]` in the index, and `forRemoval` gives `[removal]`, which `-Xlint` cannot
  turn off. Add `@SuppressWarnings({"deprecation", "removal"})` to the generated type.
- **An executor whose constructor throws a checked exception passes every check** (`SubscribeStep.java:272-275`), and
  the generated `Ex::new` does not compile, with the error in generated code. Require the constructor to throw only
  unchecked exceptions, and say so in `SubscribingAnnotation`.

### Low

- Stale comment at `SubscribeStep.java:108`: "The event bus finds the index by this name". The bus matches on
  `listenerType()` since `1a598c9`.

## processing-testing and core-testing

### Low

- **`TestCompiler.compile` can leak temporary directories and hide the real failure** (`TestCompiler.java:276-303,
  406-414`): the directories are created before the `try`, and a failing `deleteRecursively` in `finally` replaces the
  original exception. Create them inside the `try`, delete each independently, and add failures as suppressed.
- **`GeneratedFile` builds its URI by concatenation** (`internal/GeneratedFile.java:25`): a resource name with a space,
  `#`, `%` or `?` makes `compile()` throw instead of returning a `Compilation`. Use the multi-argument `URI`
  constructor.
- **`hadNoWarnings()` misses deprecation and unchecked notes** (`CompilationAssert.java:136-145`): without
  `-Xlint:deprecation`/`unchecked`, javac reports them as summary notes, which the assertion ignores, while its Javadoc
  says "no warning, mandatory or not".
- **Assertions that pass vacuously**: `RangeAssert.contains()`/`doesNotContain()` (RangeAssert.java:46,68) and
  `MultimapAssert.containsKeys()`/`doesNotContainKeys()` (MultimapAssert.java:90,112) pass with no argument. Reject
  empty varargs, as AssertJ does.
- **`MultimapAssert.hasValues` collapses duplicates for set-valued keys** (`MultimapAssert.java:180-181`):
  `hasValues(k, 1, 1)` passes for `{1}`.
- **`MultisetAssert` loses order after `filteredOn`** (`MultisetAssert.java:108-112`): the filtered elements are put
  in a `HashMultiset`, so `containsExactly` on a filtered `TreeMultiset` can fail wrongly.

### Info

- `PlatformPreset`'s macOS `java.io.tmpdir` is `/tmp` with no `TMPDIR`; a real JVM has `/var/folders/…/T/` and sets
  `TMPDIR` (`PlatformPreset.java:45,261`). Only the documentation's "typically" is affected.
- `FakeTicker` and the public types of processing-testing have no `@since` (they date from 0.1.0, like `Ticker`).
- A compilation shared between tests hands the same javac `Elements` and `Types` to every test; under JUnit parallel
  execution they would be used concurrently, which javac does not support. Document it.

## Build, CI and release

No workflow runs on `pull_request_target`, no untrusted event data reaches a `run:` step, and release inputs are checked
by regular expression before use.

### Medium

**Build code runs with a write token and the signing key in reach.** `.github/workflows/docs.yml:44-45,70-79,105,113`,
`release.yml:16-17,57-74,88,103`, verified. `contents: write` applies to the whole workflow, and `actions/checkout`
keeps the token in `.git/config` (`persist-credentials` is not set). Every push to main runs `./mvnw compile` and
`package` with that token readable; the release runs `clean verify` with the token, the imported GPG key and a Maven
cache restored from main. A compromised plugin or dependency could push to main or poison `~/.m2` before signing.
Fix: in `docs.yml`, build in a job with `contents: read` and `persist-credentials: false`, and push gh-pages from a
job that runs no build code; in `release.yml`, set `persist-credentials: false`, add credentials only for the push
step, and drop `cache: maven`.

### Low

- **`release.sh` exports the Central token and GPG passphrase before the full build** (`scripts/release.sh:127`,
  verified), so every test, plugin and invoker IT inherits them. Keep them unexported and pass them to `deploy` only.
- **The wrapper does not verify Maven's checksum**: `.mvn/wrapper/maven-wrapper.properties` has no
  `distributionSha256Sum`, although `mvnw` supports it.
- **`release.yml` checks nothing before publishing** (lines 87-122): unlike `release.sh`, it does not check that the tag
  is free or that main has not moved, so an upload can succeed and the tag or push then fail. Check first, and push with
  `--atomic`.
- **Inputs interpolated into `run:`** (`release.yml:84,111-119,128-129`): safe today because they are validated
  first; pass them through `env:` as `docs.yml` does.
- **Actions pinned by tag, not by SHA**, including in the job that holds secrets; `ci.yml` uses `checkout@v5` while the
  other workflows use `@v7`.
- **`project.build.outputTimestamp` is maintained by hand in two places** (`pom.xml:67`, `bom/pom.xml:58`) and neither
  release path updates it. Set it from the release, for example in `.mvn/maven.config` next to `-Drevision`.

### Plausible

- `deploy -DskipTests` may still run the invoker ITs, with the secrets in the environment (`release.yml:103`); add
  `-Dinvoker.skip`.
- `javadoc.sh:70` links to docs.oracle.com with `-Werror`, so publishing the API depends on Oracle being reachable;
  `-linkoffline` with a committed `element-list` removes that.
- The docs workflow's concurrency group can cancel a pending run from a release when a push to main arrives.
- `SiteGenerator` copies theme subdirectories empty (`SiteGenerator.java:181-185`), once the theme has any.

## gaia-maven-plugin and the guide generator

### Low

- **`register-services` cannot remove a provider it added before** (`ProviderFiles.java:44`,
  `RegisterServicesMojo.java:72`): an emptied service file is skipped, and without `clean` the `provides` stays,
  contrary to the guide. Remove the directive when the file is empty; add an IT that builds twice without `clean`.
- **A misspelled service in `<services>` is ignored silently** (`ProviderFiles.java:42`). Fail, or warn.
- **Multi-release descriptors are ignored**: only `module-info.class` at the root is patched, and a
  `META-INF/versions/N/module-info.class` is skipped with a debug message (`RegisterServicesMojo.java:65-68`).
- **ASM failures surface as internal errors** (`ModuleInfo.java:38`): a class file newer than ASM supports throws
  `IllegalArgumentException`, which the mojo does not catch. Wrap it in a `MojoExecutionException` naming the file.
- **The guide accepts raw HTML unchecked** (`docs/.../SiteGenerator.java:165`): HTML bypasses the link check and the
  image ban. Only committers write the pages, so the risk is low; report `HtmlBlock` and `HtmlInline` nodes.

### Info

- The plugin requires Maven 3.10.0 because it is built against that `maven-plugin-api`, though it only uses
  `AbstractMojo` and the annotations: Maven 3.9 users cannot use it. Worth deciding on purpose.

## Good practices observed

- Strict build: Error Prone, NullAway, Checkstyle and `-Xlint:all -Werror` everywhere, JSpecify on every package.
- Collections: serial proxies rebuild through the public mutators; `checkModifiable()` runs before any no-op check;
  `Range` models its bounds as cuts, which makes empty and adjacent ranges correct.
- I/O: `AtomicFiles` uses exclusive creation, `ATOMIC_MOVE` without silent fallback, and fsyncs both the file and its
  directory; codecs report malformed input instead of replacing it.
- Event bus: copy-on-write registrations, so publishing takes no lock; per-thread queues are removed in `finally`;
  `ClassValue` caches hold no cross-loader references.
- memfs: a sealed node hierarchy, one read-write lock for the tree, open checks around every operation, a link-loop
  limit, and closed file systems leave the provider's registry.
- processing: string and Unicode escaping, annotation literals, type-annotation placement and import ordering were
  checked and are right; the generated-name scheme is injective and exhaustively tested.
- Release: secrets go through stdin, never the command line; scripts use `set -euo pipefail`; Central uploads wait
  for validation and are never published automatically; `release.sh --dry-run` blocks the upload twice.

## Test gaps

- Concurrency: none of the event bus, memfs locks, memfs open-versus-delete, or several threads blocked in
  `WatchService.take()` is tested from several threads.
- Tampered serial streams: no test feeds a null element, a non-positive count, or a huge length to any serial form,
  though their Javadoc promises protection.
- Processor: no test for an exported package of a named module, deprecated members, an event type generated in a later
  round, an executor constructor that throws, or record, enum and abstract listeners.
- I/O error paths: `close()` after a malformed write, slice `skip`, temporary-file permissions, long names, dangling
  links.
- Event bus: a broken provider, array events, a failing `register` subscribing nothing.
- memfs: deleted watched directory, Windows hash codes with exotic case mappings, `D:rel`, copy onto a root,
  attribute permissions, files over 2 GiB.
- Plugin: two builds without `clean`.

## Suggested order

1. The three high findings: the memfs deadlock, and the processor's multi-round and `-Werror` failures.
2. The security hardening: `AtomicFiles` permissions, serial-form allocation, CI token scope and `release.sh` exports.
3. The remaining medium findings, each with the test that reproduces it first.
4. Low and info findings as the code around them is touched.
